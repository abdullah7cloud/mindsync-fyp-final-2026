# MindSync audit before the upgrade (29 October 2026)

This audit was done on the project copy that I was about to upgrade. Everything below was read in the code or measured by running the tests. Nothing is estimated.

## 1. Baseline (measured)

| Suite | Result |
|---|---|
| Backend pytest | 220 passed, about 25 s |
| Frontend Vitest | 109 passed in 12 files |
| Browser end-to-end (Playwright) | 135 checks passed (recorded when the previous update was built) |

## 2. What the project contains

Backend (FastAPI, SQLAlchemy async, PostgreSQL in production, SQLite in tests): authentication with Argon2id and JWT, tasks, energy check-ins, a wellbeing model (logistic regression trained locally), a ranking heuristic ("what to do first"), a plain-English explanation module, a task-aware planning engine (`app/taskaware`, 12 modules), a topic study planner (`planner.py`), e-mail alerts (`notifier.py`), account export and erase (`account.py`), per-IP and per-account rate limits, security headers, and a stateless guest mode (`demo.py`).

Frontend (React, Vite): landing, login, register, password reset, and six app pages (Home, My Tasks, Study Plan, How Are You Feeling, My Progress, My Settings) plus How It Works. One shared data layer (`AppDataContext`) with two back-ends: the account API and a browser-only guest store.

## 3. What works well and must be preserved

- Authentication, password reset, rate limits, security headers, schema validation, export and erase.
- Guest mode and the move of guest data into a new account.
- The ranking heuristic and Gentle Mode (Burnout Mode) rule.
- The wellbeing model and its honest wording (it is a screening aid, not a diagnosis).
- The photographic design and the licensed photo credits.
- The existing 220 + 109 + 135 tests. They are the regression net for the upgrade.

## 4. Weaknesses found (the reasons for the upgrade)

| # | Finding | Evidence | Consequence |
|---|---|---|---|
| A1 | The planners are not connected to the task list. The topic planner and the single-task planner create tasks, but never plan across the tasks the student already has. | `PlannerPage.jsx` renders two separate planners; neither reads the whole task list for scheduling. | Two pending tasks due on the same day can each look feasible alone and be impossible together. |
| A2 | The focus timer is not tied to a task. | `FocusTimer` receives a title only, and logs a session only when started from a plan. | No real study history, so estimates cannot improve. |
| A3 | Energy check-ins change the single "do this first" suggestion only. | `recommend.py` uses energy; nothing re-plans. | A tired student keeps a plan made for a rested one. |
| A4 | A deadline change re-arms the 48-hour e-mail (`tasks.py` clears `reminder_sent_at`), but it does not touch any plan, because no stored plan exists. | `tasks.py` lines 90-91. | Reminders follow the deadline; schedules do not. |
| A5 | Reminders are a fixed 48 hours before, UTC only, one e-mail per task. | `notifier.py` constants and `find_due_tasks`. | No same-day or overdue alert, no time zone, no failure log, no way to choose timing. |
| A6 | Settings contain only an on/off e-mail switch. | `AlertSettings.jsx`. | There is nothing a student can tune (daily hours, break style, study times). |
| A7 | There is no profile page and no stored preferences. | No table. | Recommendations cannot reflect the student. |
| A8 | The dashboard shows counts only, with no history, no trends and no weekly review. | `DashboardPage.jsx`, `AnalyticsPage.jsx`. | The data that exists is not turned into insight. |
| A9 | There is no external language model. The natural-language part is a keyword lexicon. | `taskaware/analysis.py`. | Free-text such as "I have a stats exam in 10 days and I don't know chapter 5" is handled only by keywords. |
| A10 | The previous Smart Planner section (update 19) was judged "not connected" by the student and was rolled back on the laptop. | Student feedback, 29 October 2026. | The new design must be one connected page, with an evaluate / final-report step. |

## 5. Security review of the existing code (read, not just assumed)

Present: Argon2id in a worker thread, JWT with expiry, login lock-out, sign-up limit, owner-filtered queries (IDOR defence), pydantic validation with length and range limits, security headers, constant error text on login and reset, no password hash in the export, reset tokens stored hashed. No finding that blocks the upgrade. New code must keep these properties and add: server-side-only AI key, input delimiting against prompt injection, output validation, spend and call caps.

## 6. What the upgrade must not break

Guest mode stays stateless on the server. New tables are added with `create_all` only; no existing table is altered, so an existing database keeps working. The export and erase routes are extended to cover every new table.

## 7. Decision

Build on the existing task-aware engine as the deterministic core and add: a settings and profile store, a multi-task scheduler, an AI layer with strict validation and a local fallback, a session-feedback loop, and a reminder overhaul. The student-facing app becomes five pages: Smart Planner, Dashboard and History, Student Toolkit, Settings, My Profile.
