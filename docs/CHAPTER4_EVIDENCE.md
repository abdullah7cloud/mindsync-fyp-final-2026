## C. Latency (target: 95% of end-to-end API requests under 3 s)
**Laptop, before the fixes** (local PostgreSQL, Windows, memory use about 95%): single user fine (`/recommend` median 73.8 ms), but "10 students at once" **failed**: median 1,952 ms, p95 12,826 ms, 3 of 100 requests timed out after 15 s. Kept in `docs/latency_results.md`.
**Diagnosis** (`run-diagnose-db.bat`): a new PostgreSQL connection took about 360 ms (7 ms on Linux); RAM 95% used (0.37 of 7.7 GB free). Connections opened only on demand: p95 449 ms for 10 parallel queries; pool opened in advance: p95 97 ms.
**Fixes:** (1) connection pool opened in advance (`app/database.py`); (2) Argon2id hashing moved to worker threads (`app/security.py`; test: with four hashes running, the old code froze the event loop for 0.53 s). Plus a private error log (`backend/logs/backend_errors.log`: error type and code lines, never messages or user data).
**Laptop, after the fixes, PostgreSQL running** (`run-benchmark.bat`, 50 requests per endpoint, 20 tasks):
| Endpoint | Run 1 median / p95 | Run 2 median / p95 |
|---|---|---|
| GET /recommend | 116.9 / 189.1 ms | 90.9 / 153.3 ms |
| GET /tasks | 73.2 / 130.8 ms | 59.8 / 141.8 ms |
| POST /planner/plan | 63.7 / 107.3 ms | 45.8 / 97.1 ms |
| POST /wellbeing/assess (real model) | 87.7 / 177.2 ms | 74.9 / 140.2 ms |
| GET /recommend, 10 students at once, 100 requests | 1,476 / **2,948 ms** (max 4,307 ms) | 933 / **1,663 ms** (max 2,999 ms) |
All 100 concurrent requests succeeded in both runs; p95 is under the 3 s target both times, but only narrowly in run 1, and the slowest single request exceeded 3 s in run 1. Say this plainly. Ranking engine alone, laptop: 1000 tasks median 25-30 ms.
Interpretation: this laptop is memory-starved; one `/recommend` takes about 100 ms here against about 6 ms on a Linux machine in the build environment, so the remaining slowness is the machine, not the algorithm. Not tested: more than 10 simultaneous users.

## D. Trained models
**Task-fit model** (`docs/ML_MODEL.md`): simulated data, 20,000 rows, 60/20/20 split, validation-based choice. Test ROC-AUC 0.7225, accuracy 0.686, Brier 0.205; 5-fold CV AUC 0.7246; formula-as-predictor baseline 0.5808. LIMITATION: labels are simulated, so this shows the pipeline works, not real-world accuracy. Experimental, off by default.
**Wellbeing model** (`docs/WELLBEING_MODEL.md`, `backend/ml_training/wellbeing_metrics.json`): University Student Stress Dataset (Mendeley, DOI 10.17632/rc5htd5dfr.1, CC BY 4.0), 3,000 rows, no missing values, no duplicates; classes Low 1,243, Medium 1,431, High 326. Split 1,800 / 600 / 600 (seed 42). Eight questions (three of the dataset's questions have zero effect on its score and were dropped). Shipped model: logistic regression, C = 1. **Test set (600 students): accuracy 0.9967, macro-F1 0.9936, ROC-AUC 1.0, log-loss 0.0858**; always-guess baseline accuracy 0.4767, macro-F1 0.2152; 5-fold CV macro-F1 0.9952 (std 0.0039); 95% bootstrap interval for accuracy 0.9917-1.0000; calibration error (ECE) 0.0734, Brier 0.0383. Random forest 0.8517 and gradient boosting 0.8767 accuracy. Per class (precision / recall): Low 1.00 / 1.00, Medium 0.993 / 1.00, High 1.00 / 0.969; 2 mistakes in 600.
Reproduced independently three times with identical results: in the original training run, in my own re-run in the build environment, and by `train-wellbeing.bat` on the student's laptop (coefficients differ by less than 1e-14).
**Critical finding (put this in the report):** the dataset's `Stress_Score` is an exact linear formula of the answers (R squared 1.0 on all 3,000 rows; I confirmed independently that `Exam_Frequency + Assignment_Load - Sleep_Hours + Social_Media_Use + Screen_Time + (1 if no exercise else -1) - Family_Support + Anxiety_Level - 1` reproduces every score), the three levels are score cut-offs (Low <= 10, Medium 11-20, High >= 21), and all ten input columns look uniformly random (chi-square p between 0.155 and 0.862, largest correlation between two inputs 0.041). That pattern is consistent with computer-generated data; it cannot be proven from the file. So the 99.7% shows the model recovers the scoring rule, not that it predicts real stress or burnout. The notebook shipped with the dataset describes a different formula that does not reproduce the data. The app says this in "How the models work".

## E. Security testing (OWASP Top 10 2021)
Live probe (`run-security-test.bat`) against the running API on the student's laptop with the real wellbeing model: **51 / 51 checks passed** (21 Oct 2026, 19:01 UTC). An earlier laptop run before the model was installed: 46 / 46. Build environment: 51 / 51.
Checks: SQL injection, XSS payloads, IDOR/broken access control, missing/tampered/alg-none JWT, mass assignment, validation limits, brute-force lock-out, CORS, security headers, hostile text, removed cloud-AI routes, wellbeing input validation and per-user history.
Design measures: Argon2id hashing (off the event loop), JWT, parameterised queries, Pydantic + DB CHECK constraints, timing-safe login, generic error messages, rate limiting (20 sign-ups per hour per address), security headers, narrow CORS, strict model-input validation, no outside AI so no prompt-injection surface, a private error log that never stores messages or user data.
The earlier 35/35 result (5 Oct) was for the previous version that had cloud-AI routes; do not mix the two.

## G. Critical analysis points you can make (all true)
- Burnout Mode threshold trade-off: 3 check-ins (robust to noise) vs 1 (discoverable, one click); chose 1 for usability, at the cost of sensitivity to a single low reading.
- Decision to remove cloud AI: no cost, no privacy risk, no dependency, full offline behaviour, and the models can be explained and evaluated.
- The dataset's stress label is derived from a stress score, so including the score as a feature gives a falsely perfect model; it was excluded and the effect is measured.
- Demographic features were excluded for fairness and because the student cannot change them.
- The task-fit model is trained on simulated data - an honest limitation; future work: log completed/abandoned sessions and retrain.
- In-memory rate limiter resets on restart and is per-process - production would use Redis.
- localStorage JWT is XSS-exposed; httpOnly cookie + CSRF protection would be stronger.
- Single-instance, local deployment; no HTTPS locally.

## J. Task-aware planning engine (update 19, 28 Oct 2026)
**Why:** the earlier planner gave every task the same block lengths and one default effort per topic, did not use the student's skill or history, and the ranking looked only at deadline and difficulty. **What was built:** a deterministic engine that classifies the task (weighted phrase lexicon, several kinds at once, "unknown" when evidence is weak), estimates difficulty in general and for this student, gives a workload as a range with stages and methods, learns a per-kind correction from finished tasks (shrinkage estimate), schedules sessions over the days left (deadline, hours per day, deep-work limit, spaced review, buffer), asks up to three questions when the text is not enough, and gives a reason for every number. Design and limits: `docs/TASK_AWARE_ENGINE.md`; results: `docs/TASKAWARE_EVALUATION.md` (reproduce with `python scripts/evaluate_taskaware.py`).
**Evidence (build environment, SQLite):** backend 220 passed (45 new); frontend 109 passed (21 new); browser 135 of 135 (5 new: workload range and limits shown, steps and day-by-day schedule shown, a reason per session length, outcome saved, guest history holds no task text). Against the old planner on 10 author-written tasks the new engine used 15 distinct session lengths (old: 2) and scaled a 500 / 2000 / 5000 word essay to 105 / 425 / 1050 minutes (old: 50 each).
**Limits (say these in the viva):** the scenarios are written by the author; the learning experiment uses simulated students from a seeded generator; the base effort numbers are design assumptions, not measurements; the classifier is a lexicon for English study vocabulary, not a language model; no real student has used it, so there is no evidence yet that it improves planning or wellbeing. A usability test and a small study where students log real task times are the next steps. Not yet run on the laptop (`run-tests.bat`, `run-e2e.bat`).
